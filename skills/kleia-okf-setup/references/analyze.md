# Analyze

Goal: a plan the user approves. The plan holds a vocabulary (types and tags), a type and tags for every file, and the user's decisions. Nothing in the docs folder changes in this stage.

## 1. The folder

- If the user named a folder, use it.
- Otherwise run `find`, show the candidates with your recommendation, and ask. Never choose silently.

## 2. Inventory

Run `inventory --folder <dir>`. It writes `.kleia-okf/work/inventory.json`: each file's outline, lead paragraph, word count, links, existing frontmatter and git authors, plus clashes with OKF. Work from this digest. Read a whole file only when its job isn't clear from the outline and lead.

Size:
- Over 200 files: tell the user it takes a while, with the number of batches, then go ahead.
- Over 2,000 files: ask first, and offer to start with one subfolder.

## 3. The vocabulary

The vocabulary has two independent axes. **Type** is what a document is *for*. **Tags** are what it is *about*.

**Large folders:**
- Propose the vocabulary from a sample of at most 150 files that covers every subfolder.
- Then map every file in batches of about 100, appending to `plan.json` as you go.
- Never add a type in a mapping batch. If a batch has many low-confidence files, add a decision saying the vocabulary may be missing a type.

**Types: from the corpus first.**
1. **Group the files by their job**, using evidence that is already there: folder names, generator navigation (sidebars, `nav`), existing frontmatter categories and tags, and recurring title patterns ("ADR-0001", "Playbook: ...").
2. **Name each group in the corpus's own words.** If they say "playbook", the type is Playbook. Note where each name comes from in `origin`, for example "Your folder playbooks/".
3. **Give each type a one-sentence definition and a test question.** A file belongs to the type when the answer is yes.
4. **Check the rules:**
   - 3 to 8 types;
   - names are short nouns in sentence case;
   - no two types' test questions both say yes for the same file;
   - each type covers at least 2 files, or give `fewFilesReason` (for example, a changelog is one file by nature).
5. **Consensus test.** If more than 15% of files end up low-confidence, the corpus doesn't agree. Reframe with the seed types: Tutorial, Guide, Explanation, Reference, Runbook, Decision record, Policy, Meeting notes, Changelog, Design. Prefer a seed type only where it separates files better, and set `vocabularyFrom` to `"seed"`.

**Tags:**
- Take candidates from nouns that recur across titles, headings and folders. Merge synonyms and plurals.
- Lowercase kebab-case, each with a one-line meaning.
- Each tag used by at least 2 files; 1 to 5 tags per file.
- Never reuse a type name as a tag.
- Reuse the user's existing tags where they're consistent.

**Mapping:**
- Every file gets a type, tags, a confidence (`high`, `medium` or `low`) and a one-line reason.
- OKF makes every Markdown file in the folder a document, so nothing is left out. A file that fits no type well gets the closest one, at `low` confidence.
- An existing `log.md` is `"status": "log"`: kept as an update log, untouched. Act writes the root `log.md`, so a user's own root `log.md` needs a decision: recommend renaming it (to `changelog.md`, for example).
- A hand-written `index.md` (a site generator's section landing page) is `"status": "index"`: it stays as that folder's index and Act generates no index there. OKF allows a hand-written index, but no frontmatter on it (only `okf_version` on the root one, which Act adds). One with frontmatter can't be kept: the user renames it, for example to `overview.md`.
- `inventory` notes files that say they are generated by a tool. Tell the user in one line: they get frontmatter like any document, and the tool that rewrites them drops it. Nothing else changes for them.

## 4. Decisions

Each one changes the outcome, and the user can answer it from the card alone.

**What to put on a card:**
- `title`: the question in plain words. `why`: one sentence on what is at stake.
- `evidence`: the outline, frontmatter or values that show the problem.
- At most 3 `options`, each with a `consequence` saying what will happen, and exactly one `recommended`.
- "Something else" is added for you.

**When you need one:**
- **Existing `index.md` files:** one decision for all of them, with three options:
  - keep them as folder indexes (`"status": "index"`, recommended: their text and URLs stay);
  - replace them with generated indexes (`"status": "replace"`): Act overwrites each one with a listing of its folder, at the same path, so links to it keep working. Say that their own text goes, and that git still has it;
  - the user renames them to `overview.md`, so their text becomes a document and OKF generates the listing; then run `inventory` again.

  Never delete, move or edit them yourself, whatever the user answers: set the status, and Act does the rest. Say in the consequences:
  - a kept root `index.md` gets `okf_version` added, and the documents directly in the root are then listed in no index; with many of them, recommend renaming;
  - an `index.md` with frontmatter can't be kept (`plan check` refuses it): offer replace or rename. For rename, give it `"status": "rename"` with `"renameTo": "overview.md"`, and add a decision asking the user to rename it. `approve` waits until they have; then run `inventory` again and map the renamed file.
- **A clash from the inventory:** an existing `log.md`; a key OKF reads differently (Hugo's `type`, `status: wip`); TOML, JSON or broken frontmatter. Set `key` on a decision about a frontmatter key.
  - **The user's own `type`:** Act never adds a key a file already has, so without an edit these files never get their OKF type, and `plan check` refuses the plan. Offer: replace their `type` values with the planned types (recommended; say that their site generator may read `type` too, for layouts), with `{ "decision": "D1", "option": 1, "key": "type", "plan": true }`; or stop, and setup can't go on for these files.
  - Never offer "overwrite the user's key" as an option. Mapping their values (for example `wip` → `draft`) is fine, because the user chooses it.
  - For an option that maps values, add an `edits` entry naming the decision and that option (numbered from 1). Act makes the edit only if the user picks that option. For example, `{ "decision": "D2", "option": 1, "key": "status", "map": { "wip": "draft" } }`. Use `{ ..., "key": "tags", "add": true }` to add your tags to files that already have a `tags` list. Without it, those files keep their own tags.
- **Lifecycle:** only if the user asks for `status` or `stale_after` on every document, set `"lifecycle": { "status": "stable", "staleAfterMonths": 12 }`. Never set it on your own.
- **Low-confidence files:** put them all in one decision with `rows`, one row per file. `choices` lists the proposed type first, then the runner-up.
- **A taxonomy you changed:** where your vocabulary departs from terms the user already uses.

**What an option can do.** Only these: set a status (`index`, `replace`, `log`), make an `edits` entry, have the user rename or move files and then run `inventory` again, or stop. There is no skip, and nothing can be recorded under another key. Each consequence says what will actually happen. A "Something else" answer becomes one of these too; when it asks for something else (deleting a file, editing a doc), say that setup can't do it and offer the closest option.

Group similar items into one decision. Settle what you can yourself. More than about 7 decisions means you haven't grouped enough.

## 5. plan.json

Write `.kleia-okf/work/plan.json`. Paths are relative to the docs folder. Every file in the inventory appears exactly once.

```json
{
  "folder": "docs",
  "vocabularyFrom": "corpus",
  "types": [{ "id": "T1", "name": "Playbook", "definition": "...", "test": "...?", "origin": "Your folder playbooks/" }],
  "tags": [{ "name": "on-call", "meaning": "..." }],
  "files": [
    { "path": "playbooks/db-failover.md", "type": "Playbook", "tags": ["on-call"], "confidence": "high", "reason": "..." },
    { "path": "getting-started/index.md", "status": "index", "reason": "Your section landing page" }
  ],
  "decisions": [
    { "id": "D1", "kind": "Existing index.md", "title": "...", "why": "...", "evidence": "...",
      "options": [{ "label": "...", "consequence": "...", "recommended": true }] },
    { "id": "D2", "kind": "Low confidence", "title": "...", "why": "...",
      "rows": [{ "path": "guides/x.md", "choices": ["Guide", "Tutorial"], "reason": "..." }] }
  ]
}
```

Run `plan check`. Fix every error before the user sees anything. Act on the warnings where you can.

## 6. The report and feedback

Run `report`. Then show it:

- **On a machine with a browser** (not a cloud agent): run `serve`, open or give the user the address, then run `wait`.
  - If your tool can run a command in the background, run `wait` that way. Otherwise run it again each time it says "no answer yet".
  - When it prints a feedback block, pass it to `feedback`.
- **Otherwise:** show the user `.kleia-okf/work/report.html` in whatever way your tool allows, or give them its path. Ask them to press **Copy feedback** and paste it into the chat. Or they can just say `accept all`, or `accept all except D1: 2`.

When feedback arrives:
1. Pass it to `feedback` exactly as you got it: `--text`, or on stdin.
2. `feedback` applies the choices and prints notes: free text and comments.
3. Turn each note into a plan change, clear `notes`, and run `plan check` and `report`.
4. Start your reply with what changed. For decisions still open, give the card links `feedback` prints and keep the options in the report; don't restate them in chat.

**Refusals:**
- A block from an older plan: ask the user to reload the report.
- A cut-off block: ask them to copy it again.

## 7. Approval

When every decision is made and the user says they approve, run `approve --plan <id>` with the plan id shown in the report. Then tell them Analyze is done, and that Act adds frontmatter only when they say so.
